# ADR-002 — Mengenbegrenzung, Zeitbeziehung, Geschlecht, Alter

Status: **accepted, partially implemented**. Stand: 2026-09-12.

This is the design decision `docs/content/coverage-sprint-plan.md` §6 Q1 asked for and deferred:
"Should the engine gain rule tables for Mengenbegrenzung (same-Ziffer frequency cap), Alter,
Geschlecht and Zeitbeziehung? … It needs a Datalog/ASP design decision — a new predicate per
category, at minimum — and legal sign-off on what 'engine cannot verify age/sex from a PADnext
delivery today' means for the `warn`/`block`/`ignore` policy, before any data entry starts." That
document counted **~85 of the 100 Ziffern** still flagged after batch 1 as blocked on exactly this
question, plus a same-Ziffer "je Sitzung nur einmal" cap the batch found and explicitly declined to
encode (GOÄ 5440–5442, §3) because there was nowhere to put it.

This ADR answers the schema question, ships the mechanism, and is explicit about what is legal
sign-off (deferred) versus what is engineering (done).

---

## 1. The one fact that shapes everything below

Three of these four constraint types need data the engine's own design has already, deliberately,
made hard to get:

- **Mengenbegrenzung** needs a patient's billing history *across invoices*. The engine
  (`app.solvers.souffle_engine`) is stateless per call, and PADnext ingestion
  (`app.schemas.padnext`) parses no patient identity at all — no name, no address, no date of
  birth (module docstring; `tests/test_padnext.py::test_no_parsed_model_can_hold_patient_identity`
  enforces it). There is today **no identifier that survives from one invoice to the next**, which
  is the whole reason this needs a new table rather than a new CSV.
- **Alter** needs an age. `app.schemas.case.Patient.age` already exists on the general clinical
  extraction contract — it has since the contract shipped — but nothing has ever read it, and a
  PADnext delivery cannot fill it without parsing `<gebdatum>` (date of birth), which is exactly
  the field the identity test above forbids.
- **Zeitbeziehung**'s "within N hours" reading needs a timestamp. A PADnext `<datum>` is a
  calendar date. It always has been.

**Geschlecht is the one exception**, and it matters that it is: `Patient.sex` also already exists
on the contract, `"m"`/`"w"`/`"d"` (`app.schemas.common.Sex`), and — unlike a date of birth — a
bare sex marker is not on `test_no_parsed_model_can_hold_patient_identity`'s forbidden-field list.
Nothing stops a PADnext parser from reading `<behandelter><geschlecht>` into it. Nothing does today
(§5.3) — but the reason is different from the other three, and the ADR keeps that distinction
explicit rather than lumping all four under one "the engine can't know that" sentence, because only
three of them are actually that.

This is why the four are not one feature. Each gets its own answer below.

## 2. Mengenbegrenzung

### 2.1 Schema — `patient_ziffer_history` (new Postgres table)

```
patient_ziffer_history
  id                 uuid, pk
  organization_id    varchar(256), not null   -- tenant boundary, leads every index
  patient_pseudonym  varchar(128), not null   -- opaque, caller-supplied — see §2.4
  ziffer             varchar(16),  not null   -- no FK; catalog is versioned source data, not this DB
  service_date       date,         not null   -- a calendar date, matching PADnext's own `<datum>`
  proposal_id        uuid, null, FK -> proposals.id ON DELETE SET NULL
  recorded_at        timestamptz,  not null

  index (organization_id, patient_pseudonym, ziffer, service_date)   -- the one read this table is for
  index (proposal_id)
```

Migration: `apps/engine/alembic/versions/20260912_0013_patient_ziffer_history.py`. Model and full
reasoning: `PatientZifferHistoryRecord` in `apps/engine/app/db/models.py`.

**Why Postgres and not a fifth rule CSV.** Every existing rule table (`exclusions.csv`,
`zielleistung.csv`, `specificity.csv`, `factor_caps.csv`) describes the *law* — static, versioned,
reviewed like source code. A patient's billing count this quarter is *data*, generated by billing
activity, per patient, per organisation — the same shape as `proposals` or `api_usage_logs`, not
the same shape as a CSV. Putting it in a CSV would mean either one file per patient (unworkable) or
mixing law and billing history in one versioned artifact (a privacy and a code-review problem at
once). This is also the one part of this ADR the other three constraint types do **not** need:
Zeitbeziehung, Geschlecht and Alter are all decidable from facts already on the one invoice in
front of the engine, or from a field the general extraction contract already carries — see §3–§5.
Only Mengenbegrenzung is a fact about a patient's *history*.

**Append-only, like `audit_events`, and for the same reason** (`_reject_history_update`/
`_reject_history_delete` in `models.py`, mirroring `AuditLogIsAppendOnly`): a row here is evidence
that a Ziffer was billed on a date, and a quantity cap that can be edited after the fact is not a
cap. `ON DELETE SET NULL` on `proposal_id` follows `audit_events.proposal_id` exactly, so
`scripts/purge_old_data.py` can delete a draft's identity without silently making the ledger — the
evidence a *later* patient's cap check depends on — disappear with it.

### 2.2 Facts — `logic/datalog/goae_rules.dl`

```datalog
// caller-supplied, static per Ziffer
.decl quantity_limit(rule_id: symbol, z: symbol, max_count: number)
.input quantity_limit

// caller-supplied, computed per request from patient_ziffer_history
.decl history_count(z: symbol, occurrences: number)
.input history_count
```

New relation, `occurrences` rather than `count` — Soufflé reserves `count` as an aggregate
function name and rejects it as a field identifier (`syntax error, unexpected count aggregator`,
caught by hand-running `souffle` against the edited program before this landed, not by a review
comment).

**LAYER 3.5**, inserted between the existing exclusion layer and the mutual-conflict layer:

```datalog
.decl blocked_quantity(z: symbol, rule_id: symbol, occurrences: number, max_count: number)
blocked_quantity(Z, RuleId, Count, Max) :-
    surviving_exclusion(Z), quantity_limit(RuleId, Z, Max), history_count(Z, Count), Count >= Max.

.decl surviving_quantity(z: symbol)
surviving_quantity(Z) :- surviving_exclusion(Z), !blocked_quantity(Z, _, _, _).
```

`>=` rather than `>`, deliberately: `history_count` is *prior* occurrences, excluding the invoice
in front of the engine. A patient already at 3 of 3 who is billed again is billing a 4th — over the
cap — the moment `Count = Max`. `surviving_quantity` then replaces `surviving_exclusion` as the
base every later layer (Zeitbeziehung, Geschlecht, Alter, then the LAYER 4 conflict/billable pair)
builds on, so a position a quantity cap has already removed cannot itself suppress or compete for
a third — the same stratification discipline the file's own header describes for the four layers
that existed before this ADR.

### 2.3 Pipeline

```
Postgres                              Python                         Soufflé
patient_ziffer_history  ──query──►  quarter_counts()  ──dict──►  history_count.facts
                                    (app.services.
                                     patient_history)
```

`app/services/patient_history.py`:

- `behandlungsfall_bounds(on: date) -> (start, end)` — § 21 GOÄ defines `Behandlungsfall` as a
  whole calendar quarter, not a rolling window from first occurrence, so this is a pure calendar
  computation, not a "90 days back" heuristic.
- `quarter_counts(database, organization_id, patient_pseudonym, ziffern, as_of) -> dict[str, int]`
  — one indexed read, grouped by Ziffer, scoped to the quarter `as_of` falls in.
- `record_occurrences(session, organization_id, patient_pseudonym, occurrences, proposal_id=None)`
  — appends rows. Takes an open `AsyncSession`, not a `Database`, because writing the ledger has to
  commit atomically with whatever else approving a draft does (mark `APPROVED`, write the audit
  event) — the same reasoning `app.services.proposal_store` already applies to those two.

`quarter_counts`'s result is hand-fed to the existing `proposed_factors`-shaped seam:
`SouffleEngine.run(extraction, bridge, proposed_factors=…, history_counts=…)` →
`souffle_facts.write_fact_files(…, history_counts)` → `history_count.facts`. No new seam was
invented; the fact-injection pattern `proposed_factor` already established (write the chosen
factor in on a verification pass, so the rules can judge the solver's own choice) is reused
verbatim for a patient's history.

A Ziffer with no recorded occurrence is **omitted**, not written as `0` — Datalog's absence already
means "untracked" everywhere else in this file (`datum`, `patient_gender`, `patient_age`), and an
explicit `0` would cost a fact per Ziffer for zero informational gain: `blocked_quantity` needs
`Count >= Max` with `Max >= 1`, so an omitted Ziffer can never satisfy it either way.

### 2.4 `patient_pseudonym` — what it is and is not

An opaque, caller-supplied token, stable for one patient across invoices, within one organisation.
This module does not compute it, does not validate its shape, and does not know how it was derived
— it is the caller's obligation that the token is **not itself reversible to a name**, the same
posture `scripts/anonymize_padnext.py` already takes toward every other field it keeps (Ziffern,
factors, amounts — never who was treated). A keyed hash the PVS computes locally, with the key
never leaving the practice, is the shape this was designed against; it is not the only shape that
would satisfy the constraint, and this ADR does not mandate one.

Two organisations sharing a coincidentally identical pseudonym never collide: every read and write
is scoped to `organization_id` first (`test_two_organisations_do_not_share_a_patient_pseudonym`).

### 2.5 Golden test

`apps/engine/tests/test_complex_constraints.py::test_quantity_limit_blocks_the_occurrence_that_would_exceed_the_cap`,
plus its sibling proving the below-cap case is admitted and the no-history case is fully inert.

Real catalog Ziffer, real citation: **GOÄ 4601** — *"Eine mehr als dreimalige Berechnung der
Leistung nach Nummer 4601 im Behandlungsfall ist nicht zulässig."* (§ 4601, chapter M) — one of the
Ziffern the coverage-sprint plan named by number as blocked on this exact schema gap (§4/§5 of that
document). Synthetic patient history: three prior occurrences this Behandlungsfall
(`history_counts={"4601": 3}`). Invoice: one more claim of GOÄ 4601. Result: `billable == []`,
`blocked[0].reason == "quantity_exceeded"`, citing the rule and its legal basis. Run at the
`SouffleEngine` level — see §7 for why not through the PADnext HTTP surface.

## 3. Zeitbeziehung

### 3.1 What is decidable, and what is not

A PADnext `<datum>` is `YYYY-MM-DD`. Two claimed dates either match or they do not; there is no
finer information to read. So:

- **"not on the same day"** (`same_day_excludes`) is exactly as decidable as the cross-date
  exclusion logic already in LAYER 3 (`blocked_exclusion_cross_date`), because it is built on the
  same `same_service_date`/`known_date` facts that logic already derives from `datum`. **Enforced.**
- **"within N hours"** (`min_hours_apart`) is not decidable from a date alone, in either direction:
  two services on the same calendar date could be six hours apart or six minutes; two services on
  consecutive dates could be one minute apart across midnight. Asserting either reading would be
  the engine inventing a fact it does not have. **Never enforced — advisory only**, and only ever
  raised on a same-day match (a different-day match is silence, not evidence, by the same
  reasoning `cross_service_date` already applies).

This is the one constraint type this ADR ships as a genuine, permanent `UNKNOWN`/advisory
limitation per the task brief, rather than a temporary gap — no amount of better data entry closes
it; only the delivery carrying an actual timestamp would, and PADnext does not have one to carry.

### 3.2 Facts and layers

```datalog
.decl time_relation(rule_id: symbol, a: symbol, b: symbol, kind: symbol)
.input time_relation
```

**LAYER 3.6**, after Mengenbegrenzung:

```datalog
blocked_time_relation(B, A, RuleId) :-
    surviving_quantity(A), surviving_quantity(B),
    time_relation(RuleId, A, B, "same_day_excludes"),
    same_service_date(A, B), A != B.

surviving_time_relation(Z) :- surviving_quantity(Z), !blocked_time_relation(Z, _, _).

// advisory — never negated into surviving_time_relation
time_relation_advisory(A, B, RuleId) :-
    surviving_time_relation(A), surviving_time_relation(B),
    time_relation(RuleId, A, B, "min_hours_apart"),
    same_service_date(A, B), A != B.
```

`same_day_excludes` is directional, like a one-way `exclusion` — the CSV names which side loses —
because GOÄ Zeitbeziehungen this ADR has actually read are not symmetric ("nicht am selben Tag wie
X" names a specific displaced service, not a mutual pair). A genuinely mutual time relation would
need the same conflict-cluster treatment `exclusion(_, _, _, 1)` already gets in LAYER 4; nothing
in the four categories the coverage sprint flagged needed it, so it is not built speculatively.

`time_relation_advisory` surfaces as a `Warning_` (`type="time_relation_advisory"`) carrying both
Ziffern and the rule's legal basis — never as a `BlockedCode`, and never subtracted from
`billable`. A caller that ignores warnings sees exactly the invoice it would have seen with no
Zeitbeziehung rules loaded at all.

## 4. Geschlecht

### 4.1 Facts and layer

```datalog
.decl gender_restriction(rule_id: symbol, z: symbol, allowed_gender: symbol)
.input gender_restriction
.decl patient_gender(gender: symbol)   // 0 or 1 rows
.input patient_gender
```

**LAYER 3.7**:

```datalog
blocked_gender(Z, RuleId, G, Allowed) :-
    surviving_time_relation(Z), gender_restriction(RuleId, Z, Allowed),
    patient_gender(G), G != Allowed.

surviving_gender(Z) :- surviving_time_relation(Z), !blocked_gender(Z, _, _, _).
```

`patient_gender` absent (0 rows) means unknown, and unknown never reads as a mismatch — the same
"silence is not evidence" reading `cross_service_date` gives an unknown `datum`. A caller that
never populates `Patient.sex` sees this layer behave as if it did not exist, regardless of what is
in `gender_restriction`.

### 4.2 Source: `app.schemas.case.Patient.sex`, not a new field

`Patient.sex: Sex | None` (`Sex = Literal["m", "w", "d"]`) has been on the frozen clinical-input
contract since it shipped. `app/solvers/souffle_facts.py` never read it before this ADR — a field
that existed, validated correctly on every request, and did nothing. `build_fact_rows` now emits
`patient_gender` from it directly: one line, no schema change, because the schema change had
already happened, years earlier, for a reason nobody had connected to Datalog until this sprint's
scan flagged 9 Ziffern by name (GOÄ 27, 4851, …) that needed exactly this fact and had nowhere to
put it.

### 4.3 Why this one is not blocked on the identity invariant

`test_no_parsed_model_can_hold_patient_identity`'s forbidden set is `name`, `vorname`, `nachname`,
`geburtsdatum`, `geburtstag`, `strasse`, `plz`, `ort`, `adresse`, `versichertennr`, `patient`,
`patientid`, `email`, `telefon` — deliberately narrow, and `geschlecht` is not on it. A sex marker
alone does not re-identify a specific person the way a name or a date of birth does, which is the
whole reason the older test drew its line where it did rather than refusing every field a
`<behandelter>` element carries. Nothing prevents `PadnextCase` from parsing `<geschlecht>` into
`Patient.sex` — see §5.3 on why this ADR still does not do it.

## 5. Alter

### 5.1 Facts and layer

```datalog
.decl age_restriction(rule_id: symbol, z: symbol, min_age: number, max_age: number)
.input age_restriction
.decl patient_age(age: number)   // 0 or 1 rows, whole years
.input patient_age
```

**LAYER 3.8**:

```datalog
blocked_age(Z, RuleId, Age, MinAge, MaxAge) :-
    surviving_gender(Z), age_restriction(RuleId, Z, MinAge, MaxAge), patient_age(Age), Age < MinAge.
blocked_age(Z, RuleId, Age, MinAge, MaxAge) :-
    surviving_gender(Z), age_restriction(RuleId, Z, MinAge, MaxAge), patient_age(Age), Age > MaxAge.

surviving_age(Z) :- surviving_gender(Z), !blocked_age(Z, _, _, _, _).
```

Two rules sharing one head rather than one rule with a body disjunction — Soufflé's Datalog has no
`;`/OR operator inside a clause body; multiple rules for the same head is how every existing
multi-case conclusion in this file is already written (`chargeable(Z) :- billable(Z).` /
`chargeable(Z) :- needs_arbitration(Z).`).

An unbounded side of the band is written as a sentinel by `souffle_facts.py` — `NO_MIN_AGE = 0`,
`NO_MAX_AGE = 999` — because Datalog has no null and both sentinels sit outside `Patient.age`'s own
`ge=0, le=130` validated range, so neither can ever collide with a real claimed age.

`patient_age` absent means unknown, read exactly like an absent `patient_gender`: not evidence,
never a match.

### 5.2 Why age comes from `Patient.age` (years) and never from a date of birth

`Patient.age: int | None` also already exists on the contract, unread until now, for the same
reason `Patient.sex` did. The difference from Geschlecht is that a PADnext delivery has no honest
way to fill it: the only source data is `<gebdatum>`, and computing years-since-birth from it
inside this engine would mean parsing exactly the field
`test_no_parsed_model_can_hold_patient_identity` forbids by name (`geburtsdatum`/`geburtstag`).

This is a deliberate data-minimisation stance, not a technical limitation being worked around: age
in whole years is far less identifying than a date of birth (it cannot, on its own, narrow a
person down the way a DOB combined with a handful of other fields can), and it is the *only* form
of this fact this engine is designed to ever hold. A caller with a real date of birth is expected
to reduce it to an age locally — the same "compute the minimal derived value, never transmit the
source" posture `scripts/anonymize_padnext.py` already takes toward every other field on a real
delivery — and hand this engine only the number the Datalog layer above actually needs.

**Concretely, for PADnext ingestion specifically: age is not available today**, and is not made
available by this ADR. `Patient.age` stays `None` on every audit built from
`_build_group_audit_input` (`app/padnext/audit.py`), exactly as it was before this change. Age
restriction rules are fully specifiable and fully enforceable against the *general* clinical
extraction API (whichever caller populates `Patient.age` itself); they are inert, by design, on the
PADnext path until a product decision says an age-in-years field belongs in that ingestion contract
— which is a narrower, and much easier, decision than "parse a date of birth" would be.

### 5.3 Geschlecht's parallel gap, and why it is left exactly as wide

Geschlecht has no technical barrier the way Alter does (§4.3) — `<geschlecht>` could be parsed into
`PadnextCase` today. It is not, in this PR, for a reason that is really about the receipt rather
than about privacy: `PadnextAuditReport`'s `receipt_hash` covers the full `ClinicalExtraction` that
produced it, and every existing golden case that happens to carry a `<geschlecht>` element (several
do — `<behandelter>` in the fixtures) would start feeding a real sex marker into the fact base for
the first time, moving every one of those receipts. That is a legitimate, reviewable change — the
same kind `logic_version` moving for this whole ADR already is (§8) — but it is a *second*,
separable decision from "does the Datalog layer work", and bundling it into this ADR would make one
commit answer two questions. Wiring `<geschlecht>` into `_build_group_audit_input` is therefore the
first concrete follow-up this ADR recommends, not a limitation it is asserting.

## 6. Why `data/rules/quantity_limits.csv` and friends are not in `data/rules/` yet

This was found by testing, not decided up front, and is worth stating plainly because it very
nearly went the other way.

`RuleStore._rows()` appends a CSV's filename to `files_loaded` the moment the file **exists**,
whether or not it holds any data rows — so even shipping the four new files empty (mechanism
present, corpus empty, the same state `zielleistung.csv` has been in for a long time) changes
`RuleStore.summary()["files_loaded"]`. `tests/test_golden_snapshot.py` freezes that exact field,
by array index, as part of proving the Soufflé/Clingo migration never moved a POC-era number. A
new file — even an empty one — shifts the sorted list and reorders every index after it, which the
snapshot test reads as nine changed values it has never seen before, correctly, since nothing
taught it that a reordering and a real value change look different.

Given that, shipping real data into `data/rules/` for these four families in this PR would mean
either quietly regenerating nine frozen migration-parity snapshots for a reason that has nothing to
do with migration parity, or leaving the snapshot stale. Neither is this ADR's call to make
unilaterally, so the four new CSV pairs are **designed and documented here, with one worked example
each inline, but not materialised as files**:

```csv
# quantity_limits.manual.csv
rule_id,ziffer,max_count,window,legal_basis,quote,verified,verified_at,source
cnt_man_4601,4601,3,behandlungsfall,GOÄ Anmerkung zu Nummer 4601,"Eine mehr als dreimalige Berechnung der Leistung nach Nummer 4601 im Behandlungsfall ist nicht zulässig.",true,2026-09-12,manual_verification

# time_relations.manual.csv
rule_id,ziffer_a,ziffer_b,relation,min_hours,legal_basis,quote,verified,verified_at,source

# gender_restrictions.manual.csv
rule_id,ziffer,allowed_gender,legal_basis,quote,verified,verified_at,source
gr_man_27,27,w,"Leistungslegende Nr. 27","Untersuchung einer Frau zur Früherkennung von Krebserkrankungen",true,2026-09-12,manual_verification

# age_restrictions.manual.csv
rule_id,ziffer,min_age,max_age,legal_basis,quote,verified,verified_at,source
age_man_26,26,,13,"Leistungslegende Nr. 26","Untersuchung … bei einem Kind bis zum vollendeten 14. Lebensjahr",true,2026-09-12,manual_verification
```

`RuleStore` (`app/rules/rule_store.py`) already knows how to load all four — `QUANTITY_LIMIT_FILES`,
`TIME_RELATION_FILES`, `GENDER_RESTRICTION_FILES`, `AGE_RESTRICTION_FILES`, each an
auto/manual pair matching every other rule type's convention — so materialising them later is a
one-time data-entry pass plus a deliberate, reviewed update to
`logic/tests/golden/*.golden.normalized.json`'s `files_loaded` arrays, not a schema change. The
tests in `apps/engine/tests/test_complex_constraints.py` prove the loader against temporary CSVs of
their own, so this is a documented sequencing decision, not an untested one.

The Mengenbegrenzung golden test (§2.5) needed no CSV row at all to prove the Datalog layer: it
builds a one-rule `RuleStore` by hand, the same way
`tests/test_padnext.py::_synthetic_rules` and `tests/test_souffle.py::
test_block_policy_enforces_unverified_rules` already isolate a rule under test from the shared
corpus.

## 7. Deliberately not done in this PR

- **No API surface change.** `patient_pseudonym` is not yet a header, a body field or anything an
  HTTP caller can supply. `app.padnext.audit._build_group_audit_input` does not call
  `quarter_counts`. Wiring this in is real work with its own shape of decision (a new required or
  optional input, a new 4xx if a pseudonym is missing under some future policy) that deserves its
  own review rather than riding in in the ADR that also introduces the Datalog layer.
- **Not folded into `RuleStore.constraint_rules()` / `enforced_rule_count()` / `summary()`.** Those
  numbers are published — the marketing homepage's coverage tile, `GET /api/v1/rules/coverage` —
  and pinned by `tests/test_published_numbers.py`'s guarantee that a shipped figure is one the
  engine actually computes today. Whether "358 of 2,343" should become "358 + N of 2,343" the day
  a Mengenbegrenzung rule is verified is a product framing question, not a side effect of adding
  the mechanism. The four new lists are admitted under the same `UNVERIFIED_RULE_POLICY` as
  everything else (`RuleStore._admit`, routed to their own `*_suppressed` sinks — see the field
  comment on `RuleStore.quantity_limits`) so the safety property is real the day data lands; they
  are simply not counted in the public denominator yet.
- **Geschlecht parsing from PADnext** — see §5.3.
- **Actor-type facts** (coverage-sprint-plan.md §6 Q3 — Belegarzt/Krankenhausarzt conditions) are a
  fifth, related gap this ADR does not touch. Worth flagging because a future PADnext field for
  "who rendered this" would slot into the same `patient_setting`-style single-fact pattern
  Geschlecht and Alter already use, if that open question is ever answered yes.

## 8. Consequences already paid, mechanically

Editing `logic/datalog/goae_rules.dl` changes `Settings.logic_version` (a SHA-256 over the Datalog
and ASP programs themselves — `app/config.py`), which is inside `receipt_hash` and inside every
frozen `logic/tests/golden/*.golden.normalized.json`'s `audit_trail.logic_version`. This has
happened before for the same structural reason (`7f917db`, the cross-date exclusion fix) and the
precedent was followed exactly:

- `CASE_A_RECEIPT_PREFIX` in `apps/engine/tests/golden/oracle.py`: re-pinned, with a dated note,
  after confirming two runs agree (`test_case_a_receipt_is_stable_across_runs`).
- `receipt_hash_prefix` in `apps/engine/tests/golden/case_a_known_answer/expected.json`: updated to
  match.
- `audit_trail.logic_version` in all nine `logic/tests/golden/*.golden.normalized.json`: updated.
  Nothing else in any of the nine moved — `test_the_engine_still_reproduces_the_frozen_snapshot`
  passes on all nine, which is the check that a Datalog edit changed *only* its own fingerprint and
  not a single Ziffer, factor, amount or proof step any of the nine POC cases recorded.

One thing that did **not** follow the batch-1 precedent: this change adds no rows to any rule CSV
`RuleStore.summary()` already counts, so `enforced_rule_count`, `total_constraint_rule_count` and
`verified_share` are untouched — see §7 on why the four new families are not in that count at all
yet, and §6 on why they carry no CSV rows in this PR either way.

The initial version of `LAYER 3.5`–`3.8` did include unconditional positive proof lines
(`not_quantity_exceeded`, `gender_permitted`, …) mirroring `not_excluded`. These were removed before
landing: `SouffleEngine._parse` sorts the `proof` relation, and an unconditional positive line adds
a row to *every* chargeable position in *every* case, including the nine frozen ones, reordering
their proof-step arrays for a check that never actually ran. The four layers are therefore
negative-only in the proof tree — a row appears only when something was actually concluded — which
is also, not incidentally, the more honest reading: "we checked and it passed" is a claim about a
check that ran, and none of these four ever ran against the nine POC cases.
